# DECISIONS

Формат: дата — решение — потому что причина.

- 2026-09-05 — Источник истины по логике MVP: `Convoy_mind_diagramm.pdf`; docx — для UX-формулировок и целевого экрана — потому что PDF конкретнее и новее.
- 2026-09-05 — Пользователь MVP: водитель, телефон, портрет — потому что так сказал владелец продукта; диспетчерский сценарий откладываем.
- 2026-09-05 — Роутинг: TomTom Orbis Routing v2 `calculateRoute` (POST) — потому что v1 в deprecation, а Orbis умеет `legs[].routeStop.pauseDurationInSeconds`, что напрямую моделирует перерывы. Ограничение: из грузовых параметров только `vehicleWeightInKilograms`, `travelMode` только `car` (см. NOT_NOW).
- 2026-09-05 — Трафик: не отдельный вызов Traffic API, а `traffic: 'live'` в том же routing-запросе — потому что один вызов закрывает два блока диаграммы.
- 2026-09-05 — Парковки: собственная схема + MSW-мок с seeded-распределением — потому что бесплатного общеевропейского API занятости нет. Немецкий открытый API Autobahn GmbH (`/services/parking_lorry`) — кандидат на реальные данные позже.
- 2026-09-05 — «Бекенд» = чистый TS-модуль `src/core` внутри Expo-проекта, без сервера — потому что для MVP сервер не нужен, а два процесса усложняют старт. Ключ TomTom в `.env` приложения (см. NOT_NOW).
- 2026-09-05 — Стек: Expo managed + TypeScript + Expo Router; тесты Jest (jest-expo) + MSW v2 (`msw/node` в тестах, `msw/native` в dev-приложении) — потому что Vitest в RN не стандарт, а MSW официально поддерживает RN через `msw/native`.
- 2026-09-05 — Первый срез без карты: маршрут показывается лентой времени; карта — второй срез — потому что ценность в расписании/конфликте, а карта в RN — самая рискованная сборочная часть.
- 2026-09-05 — Работа с Claude Code разделена на две фазы с отдельными документами (`docs/PHASE1_CORE.md`, `docs/PHASE2_APP.md`); интерфейс между ними — `docs/API_CONTRACT.md` — потому что так второй агент стартует с чистым контекстом.
- 2026-09-05 — Скаффолд: `create-expo-app@latest --template default --yes --no-agents-md` во временной папке с переносом в корень — потому что CLI отказывается работать в папке, где лежит `CLAUDE.md`, а без `--no-agents-md` он бы перезаписал наш `CLAUDE.md` своим. Встало: Expo SDK 57.0.20, RN 0.86.3, React 19.2.3, TypeScript 6.0.3.
- 2026-09-05 — Каталог Expo Router — `src/app/` (так устроен шаблон default SDK 57), а не корневой `app/`, как написано в `PHASE2_APP.md` — потому что переносить шаблон ради имени папки нет смысла; фаза 2 кладёт экраны в `src/app/`.
- 2026-09-05 — Jest: `projects` c `jest-expo/node` для `__tests__/core/**` вместо пресета `jest-expo` (iOS) — потому что iOS-окружение задаёт export conditions `['require','react-native']`, под которыми `msw/node` в `msw/package.json` экспортирует `null`, а `expo/src/winter/runtime.native.ts` подменяет `fetch` на `expo/fetch`, который в Jest — заглушка. Фаза 2 добавит второй проект `jest-expo/ios` для экранов.
- 2026-09-05 — `babel.config.js` с `babel-preset-expo` (явно в devDependencies) — потому что платформенные пресеты jest-expo передают в babel-jest только `caller` и ждут конфиг проекта; без него Jest не транспилирует даже наши TS-файлы.
- 2026-09-05 — В Jest транспилируем три ESM-only зависимости msw 2.15 (`rettime`, `@open-draft/deferred-promise`, `until-async`) через `transformIgnorePatterns` — потому что у них нет CJS-сборки, а Jest 29 не умеет `require(esm)`. Список получен перебором всех рантайм-зависимостей `msw/lib/{core,node}` и `@mswjs/interceptors`.
- 2026-09-05 — devDependencies: `@types/jest@^29` (под jest 29.7), `@types/node@^24` (под Node 24); в `tsconfig.json` явный `types: ["jest","node","expo/types"]` — потому что без явного `types` tsc 6.0.3 не находил глобалы jest/node, а `expo/types` даёт декларации CSS-модулей шаблона без сгенерированного `expo-env.d.ts` (он в `.gitignore`, создаётся только `expo start`).
- 2026-09-05 — Мок-сценарий «все парковки заняты» переключается функцией `setMockScenario()` в `src/core/mocks/scenario.ts` (шаг 4); заголовок `X-Mock-Scenario` не вводим — потому что один механизм для тестов и dev-переключателя фазы 2, и `planTrip` о моках не знает. Подтверждено пользователем.
- 2026-09-05 — Имена параметров TomTom Orbis v2 берём из документации, а не из текста `PHASE1_CORE.md` (`pauseTimeInSeconds`, query `vehicleWeight`, координаты в пути URL) — потому что иначе контракт с реальным API не совпадёт. Подтверждено пользователем; точные цитаты фиксируются на шаге 2.
- 2026-09-05 — Схема ответа TomTom взята из https://docs.tomtom.com/routing-api/documentation/tomtom-orbis-maps/v2/calculate-route (прочитано 2026-09-05 из исходного HTML страницы, не из пересказа; выжимка WebFetch дала неверное значение в примере — 10 вместо 1020). Точные имена: путь `/maps/orbis/routing/calculateRoute/{routePlanningLocations}/{contentType}`, локации «Colon-delimited», `location` = «Latitude, longitude pair»; query `key`, `apiVersion=2` («Only allowed value: 2»), `departAt` («must be specified as a dateTime»), `traffic` (`live` | `historical`), `vehicleWeight` («Weight of the vehicle in kilograms»), `travelMode` («Default value and only allowed value: car»), `routeRepresentation=polyline` («returned in the points fields»); тело POST `legs[].routeStop.pauseTimeInSeconds` («It must be 0 in the last leg (the destination)»), «number of elements in the array must be equal to the number of waypoints + 1»; ответ `routes[].summary.{lengthInMeters,travelTimeInSeconds,departureTime,arrivalTime}`, `routes[].legs[].summary`, `routes[].legs[].points[].{latitude,longitude}`. Времени по точкам в `points` нет (есть `progress[]` при `extendedRouteRepresentation`) — остаёмся на пропорции по расстоянию (NOT_NOW).
- 2026-09-05 — Фикстура `tomtom_route_example.json` = пример ответа из документации, из которого удалены только строки-плейсхолдеры `...further points/legs/progresses/sections/routes...` (после удаления поправлены висячие запятые). Значения не менялись; добавлены две запятые, пропущенные в самом примере документации после `"sectionType": "TRAVEL_MODE"` (проверено по исходному HTML — опечатка в документации). Это маршрут 1147 м / 161 с; фикстуры для сквозных тестов (~9 ч) будут синтетическими по этой схеме (шаг 3).
- 2026-09-05 — Координаты внутри ядра и в публичном контракте — `GeoPoint { lat, lon }` (`src/core/types.ts`), на проводе TomTom — `TomTomPoint { latitude, longitude }` (`api/types.ts`) — потому что `PHASE1_CORE.md` везде пишет `lat/lon`, а имена TomTom менять нельзя; конвертация в одном месте, `api/tomtom.ts`.
- 2026-09-05 — Мок TomTom — детерминированный генератор `src/core/mocks/routeGenerator.ts` вместо двух статичных JSON-фикстур из плана — потому что геометрия строится по локациям запроса, число плеч всегда = waypoints + 1, а `departureTime/arrivalTime` считаются от `departAt` с учётом пауз, так что `planTrip` может честно использовать времена из ответа. Подтверждено пользователем. Единственный статичный JSON — пример из документации (шаг 2). Параметры мока (MVP, hardcoded): 100 км/ч, точка каждые 5 км, прямые между локациями.
- 2026-09-05 — `[предположение]` В моке `routes[].summary.travelTimeInSeconds` = только время в движении (сумма плеч без пауз); `arrivalTime` пауз учитывает. Документация описывает travelTimeInSeconds только через трафик, про паузы молчит. Ядро поэтому считает вождение по `legs[].summary.travelTimeInSeconds`, а ETA берёт из `arrivalTime` — эти два поля от предположения не зависят.
- 2026-09-05 — Даты в моке TomTom — ISO в UTC (`…Z`); реальный API отдаёт с оффсетом точки отправления. Сравнивать по `Date.parse`, не по строке; форматирование времени для экрана — забота фазы 2.
- 2026-09-05 — Мок TomTom проверяет документированные ограничения (`key`, `apiVersion=2`, `legs.length = waypoints + 1`, последняя пауза 0) и отвечает 400/403 с нашим форматом `{ error }` — потому что это ловит ошибки `planTrip` в тестах; ядро смотрит только на `res.ok`.
- 2026-09-05 — Закрыто предположение из STATE: babel-preset-expo в не-production не инлайнит `process.env.EXPO_PUBLIC_*`, а заменяет на `env.X` из `expo/virtual/env`, где `env = process.env` — поэтому ключ, заданный в `jest.setup.ts`, доступен в рантайме, и тест «без ключа» может удалять переменную на лету.
- 2026-09-05 — Parking-мок: сценарий `all-full` накладывается в handler поверх результата генератора (`freeAt: 0`), генератор `parkingGenerator.ts` чистый и детерминированный — потому что сценарий — свойство мока, а не данных, и генератор тестируется без сети.
- 2026-09-05 — `confidence` в Parking-моке: «сейчас» = `Date.now()` в handler, генератор получает `now` параметром — потому что иначе тест на `confidence` зависит от часов машины, на которой идут тесты.
- 2026-09-05 — Seed генератора парковок — FNV-1a от строки `${lat},${lon}`, PRNG mulberry32, оба свои (~15 строк), без новых пакетов — потому что PHASE1 запрещает пакеты без нужды, а детерминизм «один вход → один ответ» нужен для тестов и повторного запроса парковок в шаге 7.
- 2026-09-05 — Занятость Parking-мока зависит от координат и периода суток (ночь `[22, 06)` по UTC, иначе день), а не от конкретного часа `at`; час берётся по UTC — потому что повторный запрос по сдвинутому времени в шаге 7 должен быть предсказуем в тестах; локальное время — NOT_NOW.
- 2026-09-05 — Ёмкость парковок 20–80 мест, днём занято 40–70 % (→ `freeAt ≥ 6`), ночью 85–100 % (→ бывает 0) — потому что happy path шага 7 требует свободную парковку на обоих якорях (08:10Z и 13:05Z — второй с учётом паузы на первом; раньше здесь стояло 12:20Z без паузы), а ночью конфликт должен быть возможен и без сценария `all-full`.
- 2026-09-05 — `recordRequests()` вынесен в `__tests__/core/helpers.ts` на шаге 4, раньше запланированного шага 7 — потому что понадобился для проверки query в `parking.test.ts`.
- 2026-09-05 — AETR-пороги включительные: ровно на 4:30 непрерывного и 9:00 суточного вождения ехать дальше нельзя (`>=`); при одновременном достижении приоритет `dailyRest` — потому что «после 4:30 — перерыв» читаем как «отметку 4:30 проезжать нельзя», а суточный отдых поглощает перерыв. Подтверждено пользователем.
- 2026-09-05 — Результат `nextRequiredBreak` — `{ type: 'break45' | 'dailyRest' | null, remainingSec }`, `remainingSec` = до ближайшего из двух порогов, 0 при достижении; константу суточного отдыха 11 ч не вводим — потому что `remainingSec` пригодится планировщику шага 7 (`breaks.ts` в итоге работает напрямую с константами, см. ниже), а 11 ч в MVP никто не читает (планирование дольше дня — NOT_NOW).
- 2026-09-05 — `breaks.ts`: якорь ставится линейной интерполяцией внутри сегмента ровно на пороге 4:10, а не снапом к ближайшей точке полилинии — потому что у мока точки через 5 км (±3 мин), а у реального TomTom точки плотные, и интерполяция даёт одинаково точный результат в обоих случаях.
- 2026-09-05 — `breaks.ts`: очередной якорь не ставится, если от предыдущего якоря (или старта) до финиша меньше `MAX_CONTINUOUS_DRIVING_SEC` — потому что это то же самое, что «до финиша меньше запаса 20 мин», но выражено через норму: водитель легально доезжает без перерыва. Согласуется с включительным порогом: 4:29 → 0 якорей, 4:30 → 1, 8:39 → 1, 8:40 → 2.
- 2026-09-05 — `breaks.ts` не учитывает суточный лимит 9:00, только перерывы 4:30; флаг `requiresDailyRest` ставит `schedule.ts` (шаг 7) — потому что для маршрутов до 13 ч на якоря это не влияет, а планирование дольше дня — NOT_NOW.
- 2026-09-05 — В `Anchor` сверх плана добавлено `drivenSecFromStart` — потому что шагу 7 оно нужно для пересчёта приездов по плечам вызова 2, а тесту — для точной проверки 4:10 / 8:20 без пересчёта по дистанции.
- 2026-09-05 — Якоря ставятся все сразу из вызова 1 (`placeBreakAnchors`), последовательное якорение от выбранной парковки и учёт показаний тахографа не делаем — потому что пользователь решил держаться изначального плана `PHASE1_CORE.md` шага 7; оба варианта записаны в NOT_NOW. Подтверждено пользователем.
- 2026-09-05 — Выбор парковки у якоря — ближайшая по haversine с `freeAt ≥ 1`; после вызова 2 защитная проверка «каждое плечо ≤ 4:30», иначе `conflict` с кодом `leg-exceeds-continuous-limit` — потому что парковки в 25 км от якоря могут сдвинуть остановку до ±15 мин по маршруту и в худшем случае дать плечо 4:40; на тестовом маршруте плечи 4:13. Подтверждено пользователем.
- 2026-09-05 — `conflict.nearestFreeParking` при отсутствии свободных в 25 км берётся одним дополнительным запросом с радиусом `CONFLICT_SEARCH_RADIUS_KM = 50`, только на пути конфликта; при `parking-lost-after-reroute` — из того же повторного ответа, кроме выбранной — потому что иначе полю неоткуда взяться. Подтверждено пользователем.
- 2026-09-05 — `Conflict` содержит машинный `code` и `reason` на английском; код и сообщения — на английском, документы остаются на русском — потому что проект позже переводится на английский, а русские документы нужны владельцу для понимания. Подтверждено пользователем.
- 2026-09-05 — `planTrip` без якорей (маршрут < 4:30) не делает второй вызов TomTom и отвечает по вызову 1 с `stops: []`; `Stop.departAt = arrivalAt + BREAK_SEC` считается сам, а не берётся из `legs[i+1].departureTime`; `drivingTimeSec` и `requiresDailyRest` — по сумме `legs[].summary.travelTimeInSeconds` последнего вызова — потому что второй вызов без waypoints повторил бы первый, а поля плеч не зависят от `[предположение]` про паузы в `summary.travelTimeInSeconds`.
- 2026-09-05 — Проверка «всё сходится»: `|приезд по вызову 2 − plannedArrivalAt| > MAX_ARRIVAL_SHIFT_SEC = 1800` → один повторный `getParkingsNear` по координатам якоря на фактическое время; ок, если выбранная парковка всё ещё `freeAt ≥ 1`; иначе `parking-lost-after-reroute`, без третьего вызова TomTom — потому что более одной итерации — NOT_NOW, а запрос по координатам якоря даёт тот же seed, и выбранная парковка гарантированно в ответе.
- 2026-09-05 — `src/core/index.ts` не экспортирует `mocks/native` вопреки тексту `PHASE1_CORE.md` шага 8; приложение подключает моки по прямому пути `src/core/mocks/native.ts` под `__DEV__` — потому что иначе msw и полифиллы попадают в прод-бандл; проверяется тестом `index.test.ts`.
- 2026-09-05 — Рецепт включения моков в приложении (`API_CONTRACT.md` § 6) написан через `require` внутри `if (__DEV__)` и `onUnhandledRequest: 'bypass'` — потому что ES `import` поднимается и ломает порядок «полифиллы → msw/native», а `'error'` уронил бы запросы Metro/Expo; значения опции проверены по типам msw 2.15.0, сам рецепт в приложении не запускался (`[предположение]`, первая проверка фазы 2).
- 2026-09-05 — Parking-мок переведён на сетку: мир разбит на ячейки 0.3°, в каждой детерминированно 1–2 парковки с фиксированными id, позицией, ёмкостью и коэффициентом занятости (seed от индексов ячейки); запрос любого центра и радиуса — подмножество одного множества, ближайшие первыми — потому что аудит показал: при seed от центра запросы на 25 и 50 км давали одинаковые id и `freeAt` с разными координатами, и запасной запрос на 50 км для `conflict.nearestFreeParking` не мог найти свободную парковку. «3–6 парковок в радиусе» из `PHASE1_CORE.md` теперь не константа, а плотность: у тестового якоря 3 в 25 км, 19 в 50 км. Сигнатура `generateParkings`, handler и `planTrip` не менялись; в `parking.test.ts` +3 теста на стабильность (50 ⊇ 25, соседний центр, порядок по расстоянию), проверка «3–6» заменена на «≥ 1».
